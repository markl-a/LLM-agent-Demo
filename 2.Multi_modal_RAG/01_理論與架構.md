## 引言

### 傳統 RAG 的局限性

傳統的 RAG 系統主要設計用於處理純文字內容，其基本流程為：

```
文本文檔 → 文本分塊 → 文本嵌入 → 向量庫
                                    ↓
              用戶查詢 → 查詢嵌入 → 相似度檢索 → 檢索文本塊
                                                    ↓
                                            LLM 生成答案
```

這種方法在處理包含圖像、表格、圖表等多模態內容時會遇到以下問題：

1. **資訊損失**：圖像和圖表中的視覺資訊被完全忽略
2. **語義理解不完整**：表格的結構化資訊可能被破壞
3. **檢索效果差**：無法基於視覺內容進行檢索
4. **答案質量低**：缺少關鍵視覺證據支持

### 真實世界的文檔特性

實際應用中的文檔通常具有以下特徵：

| 文檔類型 | 文字佔比 | 視覺內容 | 結構化數據 |
|---------|---------|---------|-----------|
| 技術文檔 | 60-70% | 架構圖、流程圖 | 配置表、API 參數表 |
| 財務報告 | 40-50% | 趨勢圖、餅圖 | 財務報表、指標表 |
| 研究論文 | 70-80% | 實驗圖表、示意圖 | 實驗數據表 |
| 產品手冊 | 50-60% | 產品圖、操作圖 | 規格表、比較表 |

**關鍵洞察**：在許多領域，30-50% 的關鍵資訊存在於非文字內容中。

## RAG 基礎理論

### 檢索增強生成的核心原理

RAG 結合了兩種 AI 能力：

#### 1. 資訊檢索（Information Retrieval, IR）

**目標**：從大規模文檔集合中找出與查詢相關的內容

**關鍵技術**：
- **向量化（Embedding）**：將文本轉換為高維向量空間中的點
- **相似度計算**：通常使用餘弦相似度（Cosine Similarity）

```
相似度 = cos(θ) = (A · B) / (||A|| × ||B||)

其中：
- A: 查詢向量
- B: 文檔向量
- ||A||, ||B||: 向量的歐幾里得範數
```

- **索引結構**：使用 HNSW、IVF 等算法實現高效近似最近鄰搜索（ANN）

#### 2. 生成式語言模型（Generative LM）

**目標**：基於上下文生成連貫、準確的回答

**工作原理**：
```
P(答案|查詢, 檢索內容) = LLM(查詢 ⊕ 檢索內容)

其中 ⊕ 表示上下文拼接
```

### RAG vs Fine-tuning vs Prompt Engineering

| 特性 | RAG | Fine-tuning | Prompt Engineering |
|------|-----|-------------|-------------------|
| 知識更新 | ✅ 實時 | ❌ 需重新訓練 | ⚠️ 有限制 |
| 成本 | 💰 中等 | 💰💰💰 高 | 💰 低 |
| 準確度 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 可解釋性 | ✅ 可追溯來源 | ❌ 黑箱 | ⚠️ 部分可解釋 |
| 領域適應 | ✅ 快速 | ⚠️ 慢 | ✅ 快速 |

**結論**：RAG 在大多數企業應用場景中提供了最佳的性能/成本平衡。

## 多模態處理的挑戰

### 1. 異質性數據表示（Heterogeneous Representation）

不同模態的數據具有根本不同的表示形式：

```python
# 文本：序列化符號
text = "2023年Q4營收成長25%"
# → Token IDs: [2023, 年, Q4, 營收, 成長, 25, %]

# 圖像：像素矩陣
image = np.array([[[255, 0, 0], ...], ...])  # Shape: (H, W, 3)

# 表格：結構化數據
table = {
    "headers": ["公司", "營收", "成長率"],
    "rows": [["A公司", "100M", "25%"], ...]
}
```

**挑戰**：如何在統一的檢索框架中處理這些異質數據？

### 2. 語義對齊（Semantic Alignment）

同一概念在不同模態中的表現形式不同：

```
概念：「營收成長趨勢」

文本表示：
"公司營收從2020年的50M成長到2023年的100M，年複合成長率達到25%"

視覺表示：
📈 [折線圖顯示上升趨勢]

表格表示：
| 年份 | 營收 | 成長率 |
|------|------|--------|
| 2020 | 50M  | -      |
| 2021 | 62M  | 24%    |
| 2022 | 78M  | 26%    |
| 2023 | 100M | 28%    |
```

**挑戰**：如何理解和對齊不同模態中的語義？

### 3. 檢索粒度（Retrieval Granularity）

```
文檔層級結構：
PDF 文檔
├── 章節 1
│   ├── 段落 1.1（文本）
│   ├── 圖 1.1（圖像）
│   └── 表 1.1（表格）
├── 章節 2
│   ├── 段落 2.1（文本）
│   └── 圖 2.1（圖像）
...
```

**問題**：
- 應該以什麼粒度進行檢索？（段落 vs 圖像 vs 整章）
- 如何保持相關內容的上下文關聯？
- 如何避免檢索到不相關的視覺內容？

### 4. 計算成本（Computational Cost）

處理多模態內容的成本遠高於純文本：

| 操作 | 文本 | 圖像 | 相對成本 |
|------|------|------|---------|
| 嵌入生成 | text-embedding-3-small | CLIP ViT-L/14 | 10x |
| LLM 推理 | GPT-4 (文本) | GPT-4o (視覺) | 2-3x |
| 存儲 | ~1KB/chunk | ~100KB/image | 100x |

## 技術架構詳解

### 架構 1：多模態嵌入架構

```
┌─────────────────────────────────────────────────────────────┐
│                        文檔解析層                             │
│  PDF/DOCX → [文本提取] + [圖像提取] + [表格提取]              │
└────────────────────┬────────────────────────────────────────┘
                     │
         ┌───────────┴───────────┐
         ▼                       ▼
┌─────────────────┐    ┌──────────────────┐
│  文本嵌入模型    │    │  圖像嵌入模型     │
│  (BERT/OpenAI)  │    │   (CLIP/BLIP)    │
└────────┬────────┘    └────────┬─────────┘
         │                       │
         └───────────┬───────────┘
                     ▼
         ┌─────────────────────┐
         │   統一向量空間        │
         │  (Multi-modal       │
         │   Vector Store)     │
         └──────────┬──────────┘
                     │
                     ▼
         ┌─────────────────────┐
         │   相似度檢索          │
         │ (Cosine/L2 Distance)│
         └──────────┬──────────┘
                     │
                     ▼
         ┌─────────────────────┐
         │  多模態 LLM          │
         │  (GPT-4o/Gemini)    │
         └─────────────────────┘
```

**優點**：
- 端到端可微分（如果自己訓練嵌入模型）
- 統一的語義空間，跨模態檢索自然

**缺點**：
- 依賴多模態嵌入模型的質量
- CLIP 等模型在專業領域可能表現不佳
- 難以解釋為什麼某個圖像被檢索

```
┌─────────────────────────────────────────────────────────────┐

     │        ┌────────────────────┐

     │        │ (Text Embeddings)  │
     │        └─────────┬──────────┘
     │                  │
     │                  ▼
     │        ┌────────────────────┐
     │        │   向量庫            │
     │        │ (Vector Store)     │
     │        └─────────┬──────────┘
     │                  │
     │                  ▼
     │        ┌────────────────────┐

│   多模態 LLM          │
│  (最終答案生成)       │
└──────────────────────┘
```

**核心思想**：
1. **分離檢索和生成**：用摘要檢索，用原始內容生成
2. **最佳語義理解**：LLM 生成的摘要包含豐富的語義資訊
3. **保留細節**：答案生成時使用高質量的原始圖像

#### Step 3: 多向量檢索器

**核心數據結構**：

```python
class MultiVectorRetriever:
    """
    多向量檢索器

    設計思想：
    1. vectorstore: 存儲摘要的向量（用於檢索）
    2. docstore: 存儲原始內容（用於生成）
    3. id_key: 連接兩者的唯一標識符
    """

    def __init__(self, vectorstore, docstore, id_key="doc_id"):
        self.vectorstore = vectorstore  # Chroma/Pinecone
        self.docstore = docstore        # InMemoryStore/Redis
        self.id_key = id_key

    def add_documents(self, summaries, original_docs):
        """
        添加文檔

        流程：
        1. 為每個原始文檔生成唯一 ID
        2. 將摘要+ID 存入向量庫
        3. 將原始文檔+ID 存入文檔庫
        """
        doc_ids = [str(uuid.uuid4()) for _ in original_docs]

        # 創建摘要文檔（用於向量檢索）
        summary_docs = [
            Document(
                page_content=summary,
                metadata={self.id_key: doc_id}
            )
            for summary, doc_id in zip(summaries, doc_ids)
        ]

        # 存儲摘要向量
        self.vectorstore.add_documents(summary_docs)

        # 存儲原始內容
        self.docstore.mset(list(zip(doc_ids, original_docs)))

    def invoke(self, query, k=4):
        """
        檢索流程：

        1. 向量化查詢
        2. 在摘要向量庫中檢索 top-k
        3. 根據 ID 從文檔庫中獲取原始內容
        4. 返回原始內容
        """
        # Step 1 & 2: 基於摘要檢索
        summary_docs = self.vectorstore.similarity_search(query, k=k)

        # Step 3: 獲取文檔 ID
        doc_ids = [doc.metadata[self.id_key] for doc in summary_docs]

        # Step 4: 檢索原始內容
        original_docs = self.docstore.mget(doc_ids)

        return original_docs
```

**為什麼這個設計有效？**

1. **語義豐富的檢索**：
   - LLM 生成的摘要經過優化，包含關鍵概念
   - 摘要比原始內容更適合向量檢索

2. **細節保留的生成**：
   - 原始圖像保留所有視覺細節
   - 原始表格保留精確的數字

3. **靈活性**：
   - 可以針對不同內容類型使用不同的摘要策略
   - 可以調整檢索和生成的模型獨立優化

#### Step 4: RAG 鏈構建

```python
def build_rag_chain(retriever):
    """
    構建完整的 RAG 鏈

    流程：
    查詢 → 檢索 → 內容分類 → 提示構建 → LLM 生成
    """

    # 1. 檢索層
    def retrieve(query):
        return retriever.invoke(query, k=6)

    # 2. 內容分類層
    def split_content_types(docs):
        """
        將檢索結果分為文本和圖像
        """
        texts = []
        images = []

        for doc in docs:
            content = doc if isinstance(doc, str) else doc.page_content

            if is_base64_image(content):
                # 調整圖像大小以優化成本
                resized = resize_base64_image(content, size=(1300, 600))
                images.append(resized)
            else:
                texts.append(content)

        return {"texts": texts, "images": images}

    # 3. 提示構建層
    def build_prompt(data):
        """
        構建多模態提示

        結構：
        - 系統角色定義
        - 檢索的圖像（視覺上下文）
        - 檢索的文本/表格（文字上下文）
        - 用戶問題
        """
        messages = []

        # 添加圖像
        for img in data["context"]["images"]:
            messages.append({
                "type": "image_url",
                "image_url": {"url": f"data:image/jpeg;base64,{img}"}
            })

        # 添加文本和問題
        text_context = "\n\n".join(data["context"]["texts"])
        messages.append({
            "type": "text",
            "text": f"""
你是一個專業的分析助手，擅長從文字、表格和圖像中提取資訊。

任務：根據提供的材料回答用戶問題。

材料：
{text_context}

用戶問題：{data['question']}

要求：
1. 綜合所有資料（文字、圖像、表格）
2. 提供準確、具體的答案
3. 引用具體數據支持你的回答
4. 如果資料不足，明確說明

回答：
"""
        })

        return [HumanMessage(content=messages)]

    # 4. 組裝 RAG 鏈
    chain = (
        {
            "context": retrieve | split_content_types,
            "question": RunnablePassthrough()
        }
        | build_prompt
        | ChatOpenAI(model="gpt-4o", temperature=0)
        | StrOutputParser()
    )

    return chain
```

## 核心組件深度分析

### 1. 文檔解析：Unstructured

**為什麼選擇 Unstructured？**

| 特性 | Unstructured | PyPDF2 | PDFPlumber | Camelot |
|------|--------------|---------|------------|---------|
| 文本提取 | ✅ 優秀 | ✅ 良好 | ✅ 良好 | ⚠️ 基本 |
| 表格識別 | ✅ ML-based | ❌ 無 | ✅ 規則 | ✅ 優秀 |
| 圖像提取 | ✅ 支持 | ⚠️ 基本 | ⚠️ 基本 | ❌ 無 |
| 佈局理解 | ✅ 優秀 | ❌ 無 | ⚠️ 基本 | ⚠️ 基本 |

**嵌入模型的選擇**：

| 模型 | 維度 | 性能 | 成本 | 適用場景 |

**嵌入的數學原理**：

嵌入本質上是一個函數 f: 文本 → ℝ^d，將文本映射到 d 維向量空間：

```
f("人工智能") = [0.1, -0.3, 0.5, ..., 0.2]  # 1536維
f("機器學習") = [0.15, -0.25, 0.48, ..., 0.18]  # 1536維

相似度 = cos_similarity(f("人工智能"), f("機器學習"))
      = 0.92  # 高相似度
```

**為什麼嵌入有效？**

1. **語義空間**：相似概念在向量空間中距離近
2. **上下文編碼**：考慮詞的上下文（"銀行"在金融 vs 河流語境）
3. **跨語言**：多語言模型可以對齊不同語言的語義

### 3. 向量庫：高效檢索

**向量庫的核心挑戰**：

給定查詢向量 q 和 N 個文檔向量 {d1, d2, ..., dN}，找出最相似的 k 個文檔。

暴力搜索：O(N × d) 時間複雜度 → 對於百萬級數據不可行

**近似最近鄰（ANN）算法**：

#### HNSW（Hierarchical Navigable Small World）

```
Layer 2: o ←→ o (長距離跳躍)
          ↓    ↓
Layer 1: o ←→ o ←→ o (中距離)
          ↓    ↓    ↓
Layer 0: o ←→ o ←→ o ←→ o (精確搜索)
```

**特點**：
- 時間複雜度：O(log N)
- 空間複雜度：O(N × M) where M = 鄰居數
- 適用場景：高維向量，注重查詢速度

#### IVF（Inverted File Index）

```
1. 聚類: 將向量空間分為 n 個簇
   [Cluster1] [Cluster2] ... [Cluster_n]

2. 檢索: 先找到最近的幾個簇，再在簇內搜索

3. 優化: 與 PQ (Product Quantization) 結合壓縮
```

**特點**：
- 時間複雜度：O(√N)
- 空間複雜度：O(N)
- 適用場景：超大規模數據，可接受精度損失

**向量庫選擇**：

| 向量庫 | 算法 | 規模 | 部署 | 特色 |
|--------|------|------|------|------|
| Chroma | HNSW | < 1M | 本地 | 易用，適合原型 |
| Pinecone | 專有 | > 100M | 雲端 | 全託管，高性能 |
| Milvus | IVF/HNSW | > 100M | 自部署 | 開源，功能豐富 |
| Qdrant | HNSW | < 10M | 本地/雲 | Rust，高效 |
| Weaviate | HNSW | < 10M | 自部署 | GraphQL，語義搜索 |

## 檢索策略與優化

### 1. 混合檢索（Hybrid Retrieval）

結合向量檢索和關鍵字檢索：

```python
def hybrid_retrieval(query, alpha=0.5):
    """
    alpha: 向量檢索權重
    1-alpha: 關鍵字檢索權重
    """
    # 向量檢索
    vector_results = vector_store.similarity_search(query, k=10)
    vector_scores = {doc.id: score for doc, score in vector_results}

    # BM25 關鍵字檢索
    bm25_results = bm25_index.search(query, k=10)
    bm25_scores = {doc.id: score for doc, score in bm25_results}

    # 混合評分
    all_doc_ids = set(vector_scores.keys()) | set(bm25_scores.keys())
    hybrid_scores = {}

    for doc_id in all_doc_ids:
        v_score = vector_scores.get(doc_id, 0)
        b_score = bm25_scores.get(doc_id, 0)
        hybrid_scores[doc_id] = alpha * v_score + (1-alpha) * b_score

    # 排序返回 top-k
    top_k = sorted(hybrid_scores.items(), key=lambda x: x[1], reverse=True)[:5]
    return [doc_store.get(doc_id) for doc_id, _ in top_k]
```

**為什麼混合檢索有效？**

- 向量檢索：擅長語義理解，但可能遺漏精確匹配
- 關鍵字檢索：擅長精確匹配（如產品型號、專有名詞）

**示例**：
```

- ✅ "視覺語言模型的應用"
- ❌ 可能遺漏 "GPT-4o" 精確詞

關鍵字檢索:
- ✅ "GPT-4o 技術文檔"
- ✅ "GPT-4o 圖像分析"
- ❌ 可能遺漏語義相關但不含關鍵字的文檔

混合檢索 → 兩者優點結合
```

### 2. Re-ranking

在初步檢索後，使用更強大的模型重新排序：

```python
from sentence_transformers import CrossEncoder

# 初步檢索：向量檢索 top 20
candidates = vector_store.similarity_search(query, k=20)

# Re-ranking：使用 Cross-Encoder
reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')

pairs = [[query, doc.page_content] for doc in candidates]
scores = reranker.predict(pairs)

# 重新排序
reranked = sorted(
    zip(candidates, scores),
    key=lambda x: x[1],
    reverse=True
)[:5]  # 最終返回 top 5
```

**Cross-Encoder vs Bi-Encoder**：

```
Bi-Encoder (向量檢索):
  Query → Encoder → [q1, q2, ..., qd]
  Doc   → Encoder → [d1, d2, ..., dd]
  Score = cosine([q], [d])

  優點：快速（可以預計算文檔向量）
  缺點：查詢和文檔獨立編碼，交互有限

Cross-Encoder (Re-ranking):
  [Query, Doc] → Encoder → Score

  優點：查詢和文檔聯合編碼，交互充分，精度高
  缺點：慢（每個 query-doc 對都要重新計算）
```

**最佳實踐**：
1. Bi-Encoder 快速召回 top 20-50
2. Cross-Encoder 精確重排 top 5-10

### 關鍵設計決策

#### 1. 快取策略

```python
from functools import lru_cache
import hashlib

class RAGSystem:
    def __init__(self):
        self.summary_cache = {}  # 摘要快取
        self.retrieval_cache = LRUCache(maxsize=1000)  # 檢索快取

    def get_or_generate_summary(self, content, content_type):
        """快取摘要，避免重複生成"""
        cache_key = hashlib.md5(content.encode()).hexdigest()

        if cache_key in self.summary_cache:
            return self.summary_cache[cache_key]

        summary = self.generate_summary(content, content_type)
        self.summary_cache[cache_key] = summary
        return summary

    @lru_cache(maxsize=100)
    def retrieve(self, query):
        """快取檢索結果（短時間內相同查詢）"""
        return self.retriever.invoke(query)
```

```python
def tiered_rag_strategy(query, complexity_threshold=0.5):
    """根據查詢複雜度選擇處理策略"""
    complexity = estimate_query_complexity(query)

    if complexity < complexity_threshold:
        # 簡單查詢：只用文本，使用便宜的模型
        docs = retrieve_text_only(query)
        answer = cheap_llm.invoke(query, docs)
    else:
        # 複雜查詢：多模態，使用強大的模型
        docs = retrieve_multimodal(query)
        answer = powerful_llm.invoke(query, docs)

def estimate_query_complexity(query):
    """估計查詢複雜度"""
    factors = {

        "visual": has_visual_intent(query),  # 是否需要視覺
        "reasoning": requires_multi_hop_reasoning(query)
```

```python
            # 測試檢索
            start = time.time()
            retrieved_docs = self.rag.retrieve(query)
            latency = time.time() - start

            # 計算 Precision 和 Recall
            relevant_retrieved = set(retrieved_docs) & set(ground_truth_docs)
            precision = len(relevant_retrieved) / len(retrieved_docs)
            recall = len(relevant_retrieved) / len(ground_truth_docs)

            results["retrieval_precision"].append(precision)
            results["retrieval_recall"].append(recall)
            results["latency"].append(latency)

            # 測試生成
            answer = self.rag.generate(query, retrieved_docs)

            # 評估答案（使用 LLM 作為評判）
            faithfulness = self.evaluate_faithfulness(answer, retrieved_docs)
            relevance = self.evaluate_relevance(answer, query)

            results["answer_faithfulness"].append(faithfulness)
            results["answer_relevance"].append(relevance)

        return {k: np.mean(v) for k, v in results.items()}

    def evaluate_faithfulness(self, answer, docs):
        """評估答案是否基於檢索文檔"""
        prompt = f"""
        判斷答案是否基於提供的文檔，沒有憑空捏造。

        文檔：{docs}
        答案：{answer}

        評分（0-1）：
        """
        score = self.evaluator_llm.invoke(prompt)
        return float(score)

    def evaluate_relevance(self, answer, query):
        """評估答案是否回答了問題"""
        prompt = f"""
        判斷答案是否恰當地回答了問題。

        問題：{query}
        答案：{answer}

        評分（0-1）：
        """
        score = self.evaluator_llm.invoke(prompt)
        return float(score)
```
